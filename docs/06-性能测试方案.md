## 1. 项目背景与测试目标

### 1.1 项目背景

本项目是 **JMeter 分布式性能测试平台**，采用 Master + Agent 架构：

- **Master（控制面）**：提供项目、脚本（JMX）、场景、环境、交易、执行记录、定时任务、压力机、用户与成员、文档资产等管理能力；负责任务下发、执行状态汇聚与指标存储。
- **Agent（压力机端）**：部署在各压力机上，主动与 Master 建立 WebSocket 长连，接收任务后拉起 JMeter 子进程执行，并回传心跳、指标与产物。
- **使用者**：测试工程师通过前端（Vue3，另行建仓）调用 Master 的 REST API 完成测试资产编排与压测执行。

平台近期新增了**文档资产管理与解析入库**能力：用户上传测试方案/SLA/架构文档（docx/pdf）、环境清单与交易清单（xlsx），系统异步解析——文本类文档经清洗、切块、Embedding 向量化后写入 Qdrant 向量库，清单类文档按列映射规则抽取为环境/交易结构化数据——为后续基于 RAG 的智能助手提供知识库。该功能目前需完成功能验证。

### 1.2 本次测试的两个目的

| 目的 | 范围 | 性质 |
| --- | --- | --- |
| **目的一：压测平台核心接口性能测试** | 脚本、场景、项目、环境、交易、压力机、用户、成员、执行记录、指标查询、文档资产管理等接口 | **性能测试**（基准/单交易负载/混合/稳定性） |
| **目的二：文档上传与 embedding 入库功能验证** | 文档上传 → 异步解析 → 切块 → Embedding → Qdrant 入库 → 检索验证的端到端链路 | **功能测试**（验证正确性，不做并发 TPS 压测；用例维护在《05-平台测试方案》） |

> 明确边界：**本次性能测试不涉及大模型部分**（`/chat`、`/chat/stream`、`/reports/generate`、`/metrics/llm` 等 LLM 编排接口不在性能范围内）。Embedding 外部 API 调用作为文档入库功能的依赖项，仅在功能验证中校验其可用性，不对其进行 TPS 压测。

### 1.3 已有性能结论（继承）

前期已对登录接口完成基准与瓶颈定位（详见 `docs/perf-monitoring-and-login-bottleneck.md`），本次方案继承：

- 登录 `POST /api/v1/auth/login` 基准 646ms；密码校验使用 bcrypt cost=12，单次约 **191ms 纯 CPU**，单核理论容量约 5.2 TPS；
- Master 以 uvicorn 单进程运行，bcrypt 同步调用会短暂阻塞事件循环；
- **决策：登录不做持续 TPS 压测**。压测脚本中每个虚拟用户只登录一次（或每 Token 周期一次）换取 JWT，后续业务请求用 Token 持续施压。

### 2.2 技术栈

| 层 | 技术 | 说明 |
| --- | --- | --- |
| Master | FastAPI + SQLAlchemy 2.0 async + Python 3.12 | 全异步 I/O；CPU 密集任务用 `asyncio.to_thread` 卸载 |
| Agent | websockets + httpx + psutil | JMeter 进程树管理与 5s 批次指标采集 |
| 元数据库 | MySQL 8.4 | 连接池 `pool_size=10, max_overflow=20, pool_pre_ping=True` |
| 指标存储 | Elasticsearch 8.14（单节点，JVM 1g） | 时序 `pt-metrics-yyyy.MM.dd`、汇总 `pt-summary-{run_no}` |
| 文件存储 | MinIO | bucket `ptp`；资产 key `assets/{asset_id}/{filename}` |
| 向量库 | Qdrant v1.19.1（单容器） | collection `pt_knowledge`，向量维度 1024；REST 6333 / gRPC 6334 |
| 调度 | APScheduler AsyncIOScheduler + SQLAlchemyJobStore | 定时场景触发 + 文档解析一次性延迟任务（`coalesce=True`） |
| 文档解析入库 | python-docx / openpyxl / pdfplumber；LangChain OpenAIEmbeddings → Qdrant | 切块 chunk_size=500/overlap=50，embedding batch=64、timeout=30s、重试 3 次 |
| 部署 | Docker Compose | 平台侧 `deploy/docker-compose.yml`；监控 stack overlay 叠加 |

### 2.3 文档上传与入库链路（功能验证对象）

该链路是文档资产管理的后台处理，与压测执行链路相互独立，本次**仅做功能验证**，不做 TPS 压测。

**链路 A：上传（同步）**

1. JWT 鉴权 + 项目成员门禁（editor 及以上）；
2. 扩展名与资产类型匹配校验：plan_doc/sla_doc/architecture_doc → docx/doc/pdf；env_inventory/txn_inventory → xlsx/xls；
3. 文件读入内存计算 SHA-256，**同项目同 hash 去重**：命中则返回原资产（`reused=true`），不落 MinIO、不重复解析；
4. 新文件：MySQL 插入资产行（status=pending）→ MinIO `put_object` → 提交事务；
5. 通过 APScheduler 投递 **2s 后执行的一次性解析任务**，立即返回。

**链路 B：解析与入库（异步）**

1. 从 MinIO 拉取文件，按扩展名分发解析器（docx→python-docx、xlsx→openpyxl、pdf→pdfplumber；doc/xls/pptx 旧格式不支持 → failed），解析在 `asyncio.to_thread` 中执行；
2. **文本路**（plan_doc/sla_doc/architecture_doc）：Cleaner（去页眉/断词修复/换行规整）→ RecursiveCharacterTextSplitter 切块 → 按 batch_size=64 批量调用 Embedding API → Qdrant upsert（point_id = `crc32(asset_id:chunk_index)`，同资产重解析幂等覆盖）；
3. **结构化路**（env_inventory/txn_inventory）：按列映射规则抽取，写入 `test_environment` / `test_transaction`；
4. 状态机 CAS 推进为 ready/failed，`parse_meta` 记录 chunks/indexed/degraded/environments/transactions/warnings；
5. **降级模式（NFR-01）**：未配置 `EMBEDDING_API_KEY`/`EMBEDDING_MODEL` 时使用 FakeEmbeddings 入库（`indexed=true, degraded=true`），结构化抽取照常；
6. failed 资产可经 `POST /projects/{pid}/assets/{id}/retry-parse` 重新入队。

**链路 C：知识检索（功能验证终点）**

`GET /api/v1/assets/knowledge-search?project_id=&q=&top_k=`：将检索词向量化 → Qdrant 按 project_id 过滤做向量近邻搜索 → 返回切片内容、引用与相似度分。用于功能验证入库结果可被检索到。

## 3. 测试范围

### 3.1 性能测试范围（压测平台核心接口）

所有接口前缀 `/api/v1`，除登录、Agent 注册与 health 探针外均需 `Authorization: Bearer <token>`（HTTPBearer）；分页统一 `?page=1&page_size=20`；统一响应包裹 `{"code","message","data"}`，`code=0` 视为业务成功。

**排除项**：`/chat`、`/chat/stream`、`/reports/generate`、`/metrics/llm` 等大模型编排接口不在性能范围内；`/assets/knowledge-search` 仅在功能验证中调用，不做并发 TPS 压测。

### 3.2 功能测试范围（文档上传与 Embedding 入库）

文档上传与 embedding 入库的功能验证用例统一维护在《05-平台测试方案》，本文不展开明细。验证要点包括：上传成功/去重/类型校验/旧格式失败/解析状态机（pending→parsing→ready/failed）/文本切片入向量库/结构化抽取入表/降级模式/重试解析/检索验证入库内容。

### 3.3 范围外（Out of Scope）

- **大模型相关接口**：`/chat`、`/chat/stream`、`/reports/generate`、`/metrics/llm`——不做性能与功能压测；
- **Agent 执行压测任务的端到端能力**：JMeter 实际加压、指标 5s 批次回传、结果汇聚——属压测执行链路，另行专项；
- **WebSocket `/ws/agent`** 长连容量与协议压测；
- **前端页面**静态资源与浏览器渲染性能；
- **外部 Embedding API 的 TPS 能力**：只验证其可用性与正确入库，不对其压测；
- 多 Master 副本部署、各存储组件集群横向扩展能力（测试环境均为单节点）。

## 4. 性能测试目标与指标

### 4.1 通用指标

| 指标 | 定义 |
| --- | --- |
| 并发用户数 | 同时保持活动的虚拟用户（VU）数 |
| TPS | 每秒业务成功完成数（`code=0`；4xx 业务校验错误如 1011/3010 不计入成功，也不计入系统错误，单列统计） |
| RT | 每个请求响应时间，输出 P50/P95/P99/最大值 |
| 错误率 | 5xx + 连接超时/重置占比；业务 4xx 单独统计 |
| 拐点 | TPS 不再随并发增长、或 P95 超过阈值、或错误率 > 0.1% 时的并发点 |

### 4.2 系统资源指标（服务端）

Master 容器 CPU/内存、事件循环阻塞迹象；MySQL 连接数/慢查询/InnoDB 行锁；ES JVM/线程池（仅涉及 ES 查询时）；MinIO 请求延迟；Qdrant CPU/内存（文档上传后异步解析会写入，稳定性场景需关注）。

### 4.3 建议性能目标（基准测试后校准）

> 以下为初始建议值，**以第 6.1 节基准实测结果为基线**进行 ±20% 内修订后作为准入阈值。

| 接口类别 | P95 RT 目标 | 错误率 |
| --- | --- | --- |
| 轻量 MySQL 查询（Q-01/02/03/05/07/08/09/11/14/15，分页 20） | ≤ 300ms | 0 |
| 单条详情查询（Q-06/10） | ≤ 200ms | 0 |
| Q-04 thread-groups（MinIO+XML） | ≤ 500ms（< 500KB JMX） | 0 |
| Q-12/Q-13 ES 查询 | ≤ 800ms | 0 |
| W-01 用户新建 / W-02 删除 | ≤ 500ms（含 bcrypt ~191ms） | 0 |
| W-03 场景创建 / W-04 删除 | ≤ 500ms | 0 |
| W-05 文档上传响应（≤ 5MB，仅上传入库） | ≤ 800ms | 0 |
| 稳定性场景 | 8h 内 P95 较前 30min 漂移 < 20%，无 OOM/连接泄漏/解析任务无限积压 | < 0.1% |

## 5. 测试环境与数据准备

### 5.1 环境要求

1. 按 2.4 节启动完整平台，Master、MySQL、ES、MinIO、Qdrant 单容器同机或同网段部署，记录宿主机 CPU 核数/内存/磁盘类型；
2. 压测执行机与 Master 网络延迟实测记录（建议同机房，RT < 2ms）；
3. **文档入库功能验证**分两种配置各跑一轮：
   - 真实模式：配置 `EMBEDDING_PROVIDER`（或 `EMBEDDING_BASE_URL`）+ `EMBEDDING_API_KEY` + `EMBEDDING_MODEL`（1024 维）；
   - 降级模式：清空上述配置，确认启动日志出现 FakeEmbeddings 降级告警；
4. 监控栈按 `docs/perf-monitoring-and-login-bottleneck.md` 第 1 节提前拉起，**先建监控再压测**；
5. 每次正式场景前重启 Master 容器并确认 `/health` 正常、Qdrant collection 存在、调度器已启动（日志"启动完成"）。

### 5.2 基础数据准备

| 数据 | 数量 | 准备方式 |
| --- | --- | --- |
| admin 账号 | 1（预置） | 启动时默认用户；压测全程只用其 Token 调管理接口 |
| 普通用户 | 50 | 预建，用于混合场景查询 token 池（避免每 VU 登录） |
| 项目 | 1 个专用压测项目（如 `PERF_PROJECT`） | admin 创建并将压测用户批量加入成员 |
| JMX 脚本 | 100 个（其中 1 个带 CSV 数据文件） | 预上传，文件大小分 50KB/200KB/500KB 三档 |
| 场景 | 50 个（各挂 1~2 个脚本、1~3 个线程组） | 预建 |
| 环境/交易清单数据 | 各 200 行 | 预建或由 xlsx 资产解析落库 |
| 压力机记录 | 50 行（agent_node 造数，含 ONLINE/OFFLINE 混合） | SQL 造数，供 Q-01 keyword/status 查询 |
| 执行记录与指标 | 20 个历史 run（含 pt-summary 与 pt-metrics 索引） | 供 Q-11/Q-12/Q-13 查询压测 |
| 文档资产 | 50 个（含不同类型/状态） | 预上传，供 Q-09/Q-10 分页与状态过滤压测 |

### 5.3 文档上传功能测试文件矩阵

| 档位 | docx/pdf 文本类 | xlsx 清单类 | 用途 |
| --- | --- | --- | --- |
| S | 50~200KB（约 5 页 / 50 行） | 50KB | 基础功能验证 |
| M | 1~5MB（约 20~50 页 / 1,000 行） | 1MB | 典型业务文件 |
| L | 10~20MB（约 100+ 页 / 10,000 行） | 5MB | 大文件解析边界 |
| 异常 | doc/xls/pptx 旧格式、损坏文件、空表头清单、扩展名与类型不匹配 | — | 校验 failed 状态机与错误提示 |

每个文件准备 1 份内容副本 + 1 份用于去重路径的重复文件。

### 5.4 压测工具与脚本约定

- 工具：**JMeter 5.6+**（可用本平台自举：将压测 JMX 作为脚本上传、由 Agent 执行；也可独立 JMeter 执行）。multipart 文件上传用 HTTP Request 的 "Files Upload"；
- Token：setUp 线程组中 admin 调一次 `POST /auth/login`，JSON Extractor 提取 `$.data.token` 存为全局属性；普通用户 Token 同理预取到 CSV 池。**严禁把登录接口放进持续加压循环**；
- 动态关联：
  - W-01 用户名用 `${__time()}-${__Random(1000,9999)}` 保证唯一，提取 username 供 W-02 删除；
  - W-03 场景名同理，提取 `$.data.id` 供 W-04 删除；
  - W-05 提取 `$.data.id`，便于功能验证时轮询解析状态；
- 断言：HTTP 200 + `$.code=0`；W-01/W-03 的"重复名称"类 4xx 用独立请求验证，不混入主事务；
- 每轮场景前后执行数据清理：删除压测用户/场景/资产（含 MinIO 对象与 Qdrant 点），恢复初始数据量。

## 6. 性能测试场景设计

总体顺序：**基准 → 单交易负载 → 混合 → 稳定性**，前一场景产出作为后一场景参数输入；每场景之间留 10 分钟冷却并核对资源基线复位。

### 6.1 基准测试（Baseline）

**目的**：无竞争条件下测量每个压测平台接口单 VU 的响应时间基线，作为阈值校准与瓶颈对比依据。

**模型**：1 个 VU，迭代 50 次（W-05 每档位 10 个不同文件），循环间无思考时间。

| 事务 | 要点 |
| --- | --- |
| 全部 Q-01 ~ Q-16 | 每个接口独立线程组，固定分页 page_size=20；Q-01 分别带 keyword/status 过滤与不带参数 |
| W-01/W-02 | 每次迭代先建后删同一用户（role=普通用户） |
| W-03/W-04 | 每次迭代先建后删同一场景（单脚本、单线程组） |
| W-05 | S/M/L 三档分别上传，仅记录**上传响应 RT**（链路 A），不等待解析完成 |
| W-06/W-07 | 定时任务创建与删除/启停 |
| W-08/W-09 | 环境、交易的创建与删除 |

**产出**：各接口 P50/P95/P99 基线表；S/M/L 文件的上传 RT 基线。

### 6.2 单交易负载（Single-Transaction Load）

**目的**：对每个压测平台接口独立阶梯加压，找到 TPS 拐点、饱和点与错误率抬头点，量化单接口容量。

**通用加压模型**：阶梯线程组，每阶持续 3min、阶间不卸载，逐级加压直到触发终止条件（P95 超阈值、错误率 > 0.1%、或 TPS 连续两阶零增长）；各接口起始/步长/上限按下表，执行时按基准结果调整。

| 事务组 | 起始 VU | 步长 | 上限 | 终止 P95 阈值 |
| --- | --- | --- | --- | --- |
| 轻量查询 Q-01/02/03/05/07/08/09/11/14/15 | 10 | +10 | 100 | 300ms |
| 重查询 Q-04/06/10/Q-12/Q-13 | 5 | +5 | 50 | 500~800ms |
| W-01/W-02 用户建/删 | 2 | +2 | 20 | 500ms（关注 bcrypt CPU） |
| W-03/W-04 场景建/删 | 2 | +2 | 20 | 500ms |
| W-05 文档上传（S 档） | 2 | +2 | 20 | 800ms |
| W-05 文档上传（M 档） | 1 | +1 | 10 | 800ms |
| W-05 文档上传（L 档） | 1 | +1 | 5 | 800ms 或容器内存告警 |
| W-06/W-07 定时任务 | 1 | +1 | 10 | 500ms |
| W-08/W-09 环境/交易 CRUD | 2 | +2 | 20 | 500ms |

**注意**：W-05 阶梯压测时，JMeter 事务只计上传响应 RT（链路 A）；后台解析任务（链路 B）会自然堆积，每阶结束后需等待资产全部到达终态再升阶，避免解析任务在事件循环/线程池内累积影响下一阶上传 RT 的测量。

**产出**：每接口 VU-TPS-RT-错误率四元组曲线与拐点表。

### 6.3 混合场景（Mixed Workload）

**目的**：模拟真实日常使用中多类事务并存、读写互相干扰下的系统综合能力。

**负载模型**：并发 30 VU（按单交易结果取主要查询接口拐点的 60%~70% 修订），恒定 VU 持续 30min；各 VU 按比例随机发送事务，事务间加 1~3s 随机思考时间模拟人工操作。建议业务比例（首次执行按下表，后续按真实使用统计校准）：

| 事务 | 占比 | 说明 |
| --- | --- | --- |
| Q-01 压力机查询 | 8% | 含关键字与状态过滤各半 |
| Q-02 项目列表 | 5% | |
| Q-03 脚本查询 + Q-04 thread-groups | 12% + 3% | Q-04 取随机脚本 |
| Q-05/Q-06 场景列表/详情 | 12% | |
| Q-07/Q-08 环境/交易查询 | 8% | |
| Q-09/Q-10 资产列表/详情 | 8% | |
| Q-11/Q-12/Q-13 执行记录与指标查询 | 12% | 覆盖 MySQL 与 ES 两类存储 |
| Q-14/Q-15/Q-16 成员/插件/health | 6% | |
| W-01/W-02 用户新建+删除（成对闭环） | 3% | 即建即删，控制总量 |
| W-03/W-04 场景创建+删除（成对闭环） | 6% | 即建即删 |
| W-05 文档上传（S:M:L = 6:3:1） | 8% | 产生后台解析流，观测资源争抢 |
| W-06/W-07 定时任务 | 4% | |
| W-08/W-09 环境/交易 | 5% | |

**执行轮次**：混合场景在降级模式（FakeEmbeddings）下执行，隔离外部 API 依赖、评估 Master 自身容量；真实模式下文档上传量降低（避免外部 API 限流），仅验证上传链路与在线查询互不干扰。

**重点观测**：各事务 P95 是否满足 4.3 节目标；Master 容器 CPU 是否被文档解析的 to_thread 任务吃满导致查询 RT 抬升；MySQL 连接池占用（上限 30）；Qdrant 在持续 upsert 下的 CPU/内存；文档上传后解析任务是否全部收敛到终态（无长期悬挂在 parsing 的资产）。

### 6.4 稳定性场景（Endurance / Soak）

**目的**：长时间稳态运行下发现内存泄漏、连接泄漏、调度任务堆积、日志/慢查询累积等慢性问题。

**负载模型**：

| 项 | 配置 |
| --- | --- |
| 并发 | 混合场景容量的 **60%~70%** |
| 时长 | 试跑 2h；正式执行 **8h**（可延伸至 24h 做加强版） |
| 事务配比 | 同 6.3，W-05 降为 5%（全程约上传 700~1000 个文档，提前评估磁盘/容量） |
| 数据闭环 | 用户/场景即建即删；资产每 2h 批量清理一次（删库 + MinIO + Qdrant 点），防止库规模漂移 |
| Embedding 模式 | 以降级模式为主跑满 8h；真实模式跑 2h 补充（供应商费用与限额约束） |

**重点观测（按时间轴对比）**：

1. Master 容器内存是否单调增长（对比第 1h 与最后 1h），RSS 增幅 > 20% 需定位；
2. MySQL 空闲连接数、连接创建速率、慢查询累积；Qdrant segment 数与磁盘增长；MinIO 容量；
3. APScheduler 任务执行数与错过任务（misfire）计数；文档解析任务平均排队时长是否随时间变长；
4. 各事务分时段（每 30min 一桶）P95 曲线，后段相对首 30min 漂移 < 20%；
5. 错误率全程 < 0.1%，无 5xx 集中时段；
6. 日志中无事件循环阻塞告警、无限重试、Qdrant/MinIO 连接重建异常；
7. 结束后全量资产收敛到终态，无残留 parsing 记录。

**峰值补充（可选 Peak Stress）**：稳定性结束前以 1.5 倍稳态 VU 冲击 10min，验证过载后系统可自行回落到稳态（无雪崩、无脏数据）。

## 7. 监控与瓶颈定位

复用已搭建的 Prometheus + Grafana 全链路监控（部署细节见 `docs/perf-monitoring-and-login-bottleneck.md`）：

| 观测面 | 关键指标/面板 |
| --- | --- |
| Master 应用 | `http_request_duration_seconds_bucket{handler,method,status}`（handler 为路由模板）、`ptp_db_pool`、`ptp_scheduler_active_jobs`、`ptp_agent_online` |
| 容器/主机 | cAdvisor 容器 CPU/内存/网络（面板 14282）、node-exporter（面板 11074） |
| MySQL | 连接数、QPS、慢查询、InnoDB 行锁/缓冲池（面板 7362） |
| Elasticsearch | JVM 堆/GC、write/search 线程池队列（`elasticsearch_*` 前缀指标） |
| MinIO | `/minio/v2/metrics/cluster` 请求延迟与容量 |
| Qdrant | 容器 CPU/内存 + `GET /metrics`（向量数、segment 数） |

瓶颈定位方法论（继承既有经验）：

1. **相关性判瓶颈**：嫌疑组件的资源曲线必须与负载/RT 同步起落，恒定不变的慢指标是背景噪音；
2. 先看 Master CPU 是否单核饱和（单 worker 特征），再逐层排除 MySQL（慢查询）、Qdrant、MinIO、ES；
3. 对可疑函数在容器内直接 benchmark（如 bcrypt 191ms 的定量方法），用 ρ=到达率×单次服务时间 与 M/M/1 排队模型解释 RT 构成；
4. 文档上传接口的 RT 只含链路 A（上传入库），异步解析耗时不计入。

## 8. 准入与退出准则

### 8.1 性能测试准入

- 压测平台功能用例通过，文档上传与入库功能用例（《05-平台测试方案》）至少完成一轮真实/降级验证；
- 测试环境与监控栈就绪，基础数据（5.2 节）与文件矩阵（5.3 节）准备完成；
- 登录接口不纳入持续 TPS 压测的约定已在脚本中落实。

### 8.2 功能测试准入

- Qdrant collection `pt_knowledge` 已创建；Embedding 配置按验证模式正确设置；
- 准备好功能用例所需的文件（含正常、异常、旧格式、损坏，见 5.3 节）；
- 有数据库与 Qdrant 只读查询权限（用于核对入库行数与向量点数）。

### 8.3 通过准则

**性能**：
1. 基准、单交易结果完整，所有压测平台接口拐点不低于 4.3 节目标对应容量；
2. 混合场景全部事务 P95 达标，错误率 < 0.1%，无资产状态悬挂；
3. 8h 稳定性：P95 漂移 < 20%，错误率 < 0.1%，Master RSS 增幅 < 20%，无连接泄漏、无 misfire 累积、解析任务全部收敛。

**功能（文档上传与 embedding 入库）**：
1. 《05-平台测试方案》中文档上传与 embedding 入库用例全部通过；
2. 数据一致性检查通过：资产行与 MinIO 对象一一对应、`parse_meta.chunks` 与 Qdrant 向量点数一致、结构化行数与清单行数一致、无状态悬挂资产；
3. 真实模式与降级模式各完成一轮验证，降级模式链路不中断。

### 8.4 退出/中止条件

- Master 出现 OOM、进程重启或事件循环长时间冻结；
- MySQL/Qdrant/MinIO/ES 任一依赖不可用导致 > 5% 请求持续失败；
- 功能验证中出现资产状态机卡死（长时间停留在 parsing）或数据不一致，需先修复再继续。

## 9. 风险与注意事项

1. **单 worker 资源争抢**：文档解析 CPU 任务（`asyncio.to_thread` 使用默认线程池）与 Web 请求同进程，混合/稳定性场景需重点观测解析任务对在线查询 RT 的影响；
2. **登录接口不跑持续 TPS**：bcrypt cost=12 单核容量约 5.2 TPS 且阻塞事件循环，是已确认并接受的设计取舍；Token 在 setUp 阶段一次性获取；
3. **文件整体读入内存**：上传链路 `await file.read()` 将文件全量载入内存，L 档高并发上传需重点监控 Master 内存，必要时在单交易负载中提前触顶即停止加档；
4. **xlsx 结构化抽取的前置条件**：表头列名需命中列映射规则（如 `name`、`txn_code`、`default_script_id` 等），未命中 ≥2 个映射列时表格会被跳过并记录 warnings——功能测试文件必须按映射规则制作；
5. **异步解析计时**：性能测试中上传 RT 不含解析耗时；功能验证中需轮询资产详情观察 status 流转，轮询上限建议 5min；
6. **压测脏数据**：用户删除会级联 project_member；场景 force 删除会连带执行记录与 MinIO 产物；Qdrant 在"新切片数少于旧解析"时可能残留旧向量点，清理脚本需按 asset_id 显式删除向量；
7. **Embedding 外部依赖**：真实模式功能验证受供应商 API 可用性、限额与网络影响，失败时优先确认网络与配置，再判定系统问题；
8. 每轮场景后重置数据与容器资源基线，避免上一轮积压污染下一轮结果。
